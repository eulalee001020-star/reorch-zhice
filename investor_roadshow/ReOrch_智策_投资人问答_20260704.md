# ReOrch 智策投资人问答

版本：2026-07-04

## 1. 这是不是 APS？

当前不是完整 APS。APS 负责计划和有限产能排程，ReOrch 的首期定位是 APS、MES、ERP 之上的异常重决策操作层。我们不以首期替换 APS 为目标，而是补异常发生后的影响分析、策略选择、Top-K 候选、解释、人工确认、受控回写和经验沉淀。

长期看，ReOrch 可以从异常层升级为 AI APS，但前提是补齐初始排程、滚动排程、全约束建模、物料齐套、计划版本、发布回滚、主流系统集成和生产级 SLA。不能把这个长期目标包装成当前已完成事实。

## 2. 现有 APS 也能重排，你们的差异是什么？

不能说“APS 不能重排”。更准确的差异是：成熟 APS 通常偏计划与求解，ReOrch 从高频异常入口切入，把异常分流、影响解释、多方案取舍、人工确认、override 记录、执行反馈和案例沉淀组织成连续工作流。若客户现有 APS 已经把这条链路做得很好，ReOrch 应作为解释层、协同层、案例资产层或插件，而不是替换方案。

如果客户的目标是未来不再用其他排产系统，我们的回答应分阶段：第一阶段接在现有 APS 上方做异常层；第二阶段补齐初始排程和滚动排程；第三阶段在客户现场验证生产发布和回写安全；第四阶段再讨论替代原排产系统。

## 3. AI 到底做什么？

AI 做异常理解、策略路由辅助、推荐解释、规则候选、人工反馈结构化和经验沉淀。AI 不直接决定生产计划，不直接生成最终排程，不绕过硬约束、质量门和计划员确认。

## 4. 为什么不是通用大模型套壳？

通用大模型强在理解和表达，但不天然具备工业约束求解、排程可行性校验、幂等回写、审计、版本追踪和客户现场数据合同。ReOrch 的产品价值在于把 LLM 放进受控流程：schema、source refs、求解器、质量门、人工确认、回滚和案例库共同约束输出。

更具体地说，ReOrch 的技术内核是 Constraint-to-Recovery Technical Stack：Reality Data Layer 先判断数据能不能排；Decision Graph 表达订单、工序、资源、日历和异常关系；Constraint Compiler 把现场规则变成可审核约束；Recovery Operator Portfolio 根据异常类型选择等待顺延、替代设备、局部插入、滚动窗口或受控全局重排；Evidence-Gated Solver 再用 DataGate、ConstraintGate、EvidenceGate、ReplayGate、WritebackGate 拦截风险。LLM 只参与异常理解、规则候选、解释和反馈结构化，不是排程大脑。

## 5. 当前做到什么程度？

已经完成 MVP：后端、前端、demo 数据、异常接入、影响分析、候选方案、质量门、人工确认、mock 回写、案例沉淀、Data Readiness、Evidence Center、实验室 replay 和失败样本库。

在下一阶段主线上，已进一步补上 P0 Reality Harness、约束标定编译、历史 replay 验证、advisory-only shadow case capture 和 Agent 成本可观测的最小可运行模块。当前足够做受控试用、内部演示、只读数据验证、历史 replay 和 shadow case 采集，不应直接承诺生产无人值守调度。

## 6. 有真实客户收入吗？

当前材料没有证据证明已有真实客户收入。对外应表述为“正在从受控验证进入客户只读数据 replay / shadow mode / 付费 PoC 获取阶段”。下一步最关键里程碑是拿到 1 家付费 PoC 或明确试点协议。

## 7. Replay 采纳率能不能作为商业证明？

不能直接作为客户生产采纳率。现有 12 个 replay case 能证明系统可以记录采纳、微调、驳回和失败原因，也能证明基本闭环成立，但不能证明所有客户现场 ROI。客户商业证明必须来自真实历史异常 replay、shadow mode 和现场执行反馈。

## 8. 首批客户为什么会买？

首批客户应是复杂离散制造中异常频率高、数据基础可导出、计划员仍依赖人工重排、管理层愿意量化停机/延期/协调成本的工厂。他们更可能为“异常发生后的快速止损和可审计决策”付费，而不是为一套大而全新系统付费。

从第一性原理看，客户买单不是因为我们“有 AI”，而是因为我们降低了四类确定成本：计划失效后的等待时间、跨部门协调、错误排程带来的交付和加班损失、经验留在人身上的组织风险。

## 9. PoC 怎么避免变成数据治理项目？

用 Data Readiness 停损线。客户必须提供工单、工序、资源、当前排程、异常事件和执行反馈等最低字段。若 blocker > 0，只输出字段缺口和修复建议，不生成重排方案，不进入 ROI 统计。

## 10. 护城河是什么？

护城河不是单个求解算法，而是企业级 Recovery Policy Graph，企业异常恢复策略图谱。

它记录每一次异常的上下文、候选策略、硬约束结果、计划员选择、驳回原因和执行结果，并通过历史 replay、shadow mode 和反事实 replay 持续学习“在什么情况下，哪种恢复策略对这家企业最有效”。

它由 5 类资产组成：

- Context Fingerprint：异常类型、受影响资源、订单紧急度、slack、设备替代性、物料状态、冻结窗口、客户等级、质量状态和历史相似案例。
- Policy Portfolio：wait-and-shift、local repair、替代设备、priority swap、物料替代、加班外协、rolling window、controlled global reschedule 和 manual escalation。
- Counterfactual Replay Dataset：在同一个历史异常快照下比较多种策略，而不是只学习过去人工选了什么。
- Enterprise Preference Model：学习这家企业在交付、稳定、成本、换线、加班和关键客户之间的真实取舍。
- Outcome Feedback Loop：记录方案是否真正执行、是否二次改计划、是否实际延期、是否出现新异常。

短期护城河是产品闭环和交付模板；中期是客户历史异常 benchmark、反事实 replay、人工 override 原因和策略效果矩阵；长期是嵌入 ERP/MES/APS 之上的异常恢复策略资产。

## 11. 最大风险是什么？

- 客户数据质量不足，PoC 变成清洗项目。
- 计划员不愿在系统内确认和记录原因，资产闭环无法形成。
- 现有 APS 厂商向上补齐异常工作流。
- 工业现场回写安全、权限、审计和回滚要求高，交付周期可能拉长。
- 如果首批场景选得太大，容易陷入全厂系统替换战。

补充内容：这些风险不能回避，应该在路演中主动说明控制办法，否则投资人会认为团队低估工业软件落地难度。

## 11A. 你们到底用什么算法？

当前不是押注单一算法，而是算子组合：

- 数据层：字段映射、引用完整性、时区解析、ID crosswalk、readiness score。
- 图层：从 ScheduleSnapshot 构建 work order / operation / resource 图，沿 predecessor/successor 传播影响，得到 affected subgraph 和 repairable frontier。
- 约束层：设备能力、资源日历、冻结窗口、换型规则编译；未人工确认和未 replay 通过的 AI 规则不生效。
- 恢复层：wait and shift、alternative machine repair、local insertion、rolling window repair、controlled global reschedule。
- 求解层：启发式用于快速初解和局部搜索，CP-SAT / LNS 用于约束可行候选，timeout 时返回 best-known feasible，不包装成最优。
- 门控层：DataGate、ConstraintGate、EvidenceGate、ReplayGate、PolicyGate、WritebackGate 决定能不能求解、推荐、正式解释、shadow 或写回。

## 11B. 和传统 APS、启发式脚本、LLM Agent 有什么本质区别？

和传统 APS 的区别：我们不从替换主计划系统开始，而是从异常恢复层切入，先做只读接入、历史 replay 和 shadow mode，把计划员 override、失败样本和约束候选沉淀成资产。

和纯启发式的区别：启发式脚本通常快但难审计、约束覆盖不稳定。ReOrch 把启发式放进 Recovery Operator Portfolio，并由 ConstraintGate 和 EvidenceGate 拦截。

和纯 LLM Agent 的区别：LLM 不负责硬约束、最终排程、生产确认或写回。它只做低风险语义层，所有候选方案仍由求解器、约束校验、质量门和人工确认控制。

## 11C. 为什么不是别人两个月就能抄？

别人可以抄一个页面、一个 Agent、一个启发式求解脚本，也可以把“Top-3 方案 + LLM 解释”做成 demo。难抄的是客户现场长期沉淀的数据资产：

- 客户历史异常快照。
- 每个候选策略的反事实 replay 结果。
- 计划员采纳、微调、驳回和 override 原因。
- 执行结果、二次异常和现场反馈。
- 企业隐性约束与偏好模型。
- 行业级策略效果矩阵。
- 数据接入、约束标定、质量门和审计证据链。

ReOrch 的壁垒不在“模型参数”，而在真实数据停损、Decision Graph、约束候选生命周期、恢复算子库、Evidence Gates、Counterfactual Replay、shadow feedback、策略记忆和回写安全共同形成的闭环。

## 12. 融资后最重要的验证里程碑是什么？

1. 2-3 家目标工厂完成数据合同和场景定义。
2. 至少 10-30 条真实历史异常 replay。
3. 1 家付费 PoC 或明确试点协议。
4. shadow mode 中记录采纳、微调、驳回和 override。
5. sandbox 完成人工确认 dry-run 回写和回滚演练。
6. 第二个客户交付成本明显低于第一个客户，证明模板化复制。

## 13. 为什么不用金蝶、用友，而是 ReOrch？

金蝶、用友强在 ERP、财务、供应链、制造执行、主数据和企业级系统生态。ReOrch 不和它们正面替换，而是从异常发生后的重决策操作层切入。

企业选择 ReOrch 的理由：

- 低侵入：不要求替换 ERP/MES/APS，先只读接入数据做 replay 和 shadow mode。
- 专注高频异常：设备故障、插单、缺料、返工这些场景是计划最容易失效的地方。
- AI 不直接拍板：可执行性由求解器、规则、质量门和人工确认兜底。
- 经验资产化：接受、微调、驳回、override 都进入案例库和偏好画像。
- 可走向替代：当基础排程、约束、集成、验证和 SLA 都补齐后，ReOrch 可以逐步从异常层升级为完整排产系统。

一句话：如果客户要换核心 ERP 或财务供应链系统，选金蝶、用友；如果客户已有系统但异常发生后仍靠人、Excel、电话和会议重排，ReOrch 切得更准。

## 14. 如果目标是让企业不用其他排产系统，我们还要完成哪些工作？

必须完成八类工作：

1. 基础排程：初始排程、日/周/滚动计划、冻结窗口、计划版本、发布和回滚。
2. 全约束建模：工艺路线、设备能力、物料齐套、人员技能、工装夹具、维护窗口、外协、质量返工。
3. 数据与集成：ERP/MES/WMS/QMS/IoT 双向接口、字段映射、增量同步、幂等、数据血缘和质量看板。
4. 求解与性能：CP-SAT、启发式、规则引擎、仿真、超时可行解、最优性 gap、候选多样性和大规模压测。
5. AI 治理：Agent 分级、schema、source refs、质量门、模型版本、fallback、成本、latency 和缓存命中监控。
6. 计划员产品体验：甘特图、多视图、多方案对比、拖拽编辑、锁定工序、批量调整、协同审批。
7. 企业级运维：权限、审计、SLA、监控、告警、备份恢复、私有化部署、安全测试和应急回退。
8. 商业验证：真实历史 replay、shadow mode、sandbox 回写、付费 PoC、生产发布样板、第二客户复制。

补充内容：这不是补几个页面就能完成，而是从异常决策产品升级为完整工业软件平台。路演里可以作为长期路线，但不能说现阶段企业接入后立刻就不需要其他排产系统。
