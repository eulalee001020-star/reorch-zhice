# ReOrch 智策：实验室采用表述、数据清单与数字孪生复刻案例

版本：2026-07-04

## 1. 对外最有利但不越界的表述

当前最有利的表达不是“已经客户生产上线”，也不是“已经替代 APS”，而是：

> ReOrch 已从内部 demo 推进到合作实验室受控采用 / 验证阶段。当前正在用实验室场景、受控 replay 和数字孪生样本验证异常重决策闭环：从数据接入、排程快照、异常识别、影响分析、候选恢复方案、质量门、人工确认到经验沉淀。下一阶段将把数字孪生代理指标替换为实验室真实反馈和企业只读历史异常 replay 数据。

一句话版本：

> ReOrch 已进入合作实验室受控采用阶段，正在以数字孪生和实验室 replay 方式验证“异常发生后如何快速、可解释、可审计地恢复生产计划”。

路演版本：

> 我们当前不是停留在概念 BP，而是已经把 MVP、质量门、数字孪生 replay、实验室受控采用和计划员反馈结构化串成证据链。实验室采用的价值在于，它让系统开始进入外部专业场景，被真实使用者围绕数据、约束、策略和解释提出反馈；但我们仍然明确区分实验室验证、客户只读验证和客户生产上线。

尽调边界：

| 可以说 | 不应说 |
| --- | --- |
| 已进入合作实验室受控采用 / 试用 / 验证 | 已完成客户生产上线 |
| 已具备实验室 replay 和数字孪生代理证据 | 已证明客户现场 ROI |
| 已能记录采纳、微调、驳回和失败归因 | 计划员采纳率已经可外推到所有客户 |
| 当前用于只读验证、shadow mode 前评估和人工确认 dry-run | 可无人值守自动排产或自动写回 MES |
| 下一步把实验室和数字孪生指标迁移到企业历史异常数据 | 企业合作后立刻不需要任何其他排产系统 |

## 2. 为什么“实验室采用”是有利信号

实验室采用本质上不是商业收入证明，而是从“内部样板”到“外部专业场景”的第一层验证。它最有利的地方有三点：

1. 从内部 demo 走向外部使用者反馈：实验室会暴露字段缺失、约束建模、解释可读性、方案采纳逻辑等问题。
2. 从功能展示走向证据生产：每次 replay 都能留下输入、输出、质量门、人工复核、失败归因和版本记录。
3. 从投资人故事走向企业 PoC 准备：实验室数据结构和复刻案例可以直接转成企业只读验证的数据清单和验收指标。

[补充] 最好的 BP 口径是把实验室采用放在 Evidence Ladder 中间层：

```text
内部 MVP
-> 数字孪生复刻
-> 合作实验室受控采用
-> 企业脱敏历史数据 replay
-> shadow mode 并行验证
-> 付费 PoC
-> sandbox writeback / 生产 dry-run
```

这样既能显示项目正在推进，又不会把实验室采用包装成客户生产落地。

## 3. 实验室采用必须补齐的数据

### 3.1 合作与使用事实

| 数据项 | 为什么重要 | 推荐记录方式 |
| --- | --- | --- |
| 合作实验室名称或匿名代号 | 证明不是内部自说自话 | 对外可匿名，如 Lab-A；尽调包保留原始证明 |
| 合作开始日期 | 证明推进节奏 | 邮件、会议纪要、任务记录 |
| 使用角色 | 说明谁在用 | 实验室负责人、研究员、计划/调度相关人员 |
| 使用方式 | 区分试用、评审、共同开发 | 受控 replay、功能评审、数据映射、案例共建 |
| 使用频次 | 证明不是一次性演示 | 每周测试次数、replay case 数、反馈轮次 |
| 采用模块 | 证明采用的具体范围 | 数据映射、异常分析、候选方案、质量门、反馈沉淀 |
| 当前限制 | 防止过度承诺 | 未接生产系统、不自动写回、财务 ROI 待校准 |

### 3.2 场景与输入数据

| 数据类别 | 必须字段 | 说明 |
| --- | --- | --- |
| 工单 | `work_order_id`、产品、优先级、交期、数量 | 用于判断延期和优先级影响 |
| 工序 | `operation_id`、所属工单、工时、前后置、可用资源、能力要求 | 用于计算影响范围和可行重排 |
| 资源 | 设备、产线、工位、能力、瓶颈标记、成本 | 用于判断替代资源和瓶颈风险 |
| 日历 | 班次、停机、维护、不可用窗口 | 用于避免生成不可执行方案 |
| 物料 | 齐套状态、预计到料、替代料 | 用于判断缺料场景是否能重排 |
| 当前排程快照 | 异常发生时的计划版本、已完成/冻结工序 | 用于 replay 和 shadow mode 对比 |
| 异常日志 | 异常类型、发生时间、资源、预计恢复时间、来源 | 用于触发影响分析 |
| 人工处理方案 | 当时计划员如何改、为什么改 | 用于 Top-K 覆盖和偏好沉淀 |
| 执行结果 | 实际完工、延期、换线、加班、返工 | 用于校准 ROI，而不是只看推荐方案 |

### 3.3 验收指标

| 指标 | 当前建议口径 | 为什么要收 |
| --- | --- | --- |
| replay case 数 | 实验室阶段先 10-30 条 | 样本太少不能支撑采纳率判断 |
| 数据 readiness blocker | 必须记录为 0 或列出阻塞项 | 防止坏数据进入 ROI |
| 影响范围命中率 | 与人工复核对比 | 验证系统是否理解异常传播 |
| Top-1 直接采纳率 | 单独统计 | 反映推荐排序能力 |
| Top-K 覆盖采纳率 | 单独统计 | 反映系统是否给到有用候选 |
| 硬约束可行率 | 目标 100%，否则不能进入推荐 | 工业场景的底线 |
| 异常到候选方案时间 | 对比人工试排时间 | 证明效率价值 |
| 延期分钟变化 | 用客户/实验室口径校准 | 证明交付价值 |
| 换线/资源切换变化 | 不能只追求延期最小 | 反映执行扰动 |
| 加班/等待变化 | 连接财务估算 | 用于付费 PoC 价值测算 |
| 采纳/微调/驳回原因 | 必须结构化 | 这是经验资产壁垒 |
| 失败样本归因 | 数据、策略、约束、组织流程分开 | 失败也能变成迭代证据 |
| 审计完整率 | 输入、输出、版本、确认、反馈是否齐全 | 支撑企业 IT 和管理层尽调 |

### 3.4 AI 与成本数据

| 数据项 | 记录方式 |
| --- | --- |
| 是否调用外部 LLM | `external_llm_calls` |
| 模型名称与版本 | Agent trace |
| input / output token | 按步骤记录 |
| latency | P50 / P95 |
| 单次成本 | 按异常 case 汇总 |
| schema 通过率 | 结构化输出校验 |
| source refs 覆盖率 | 每个关键结论是否可追溯 |
| fallback 次数 | 模型低置信或失败时是否降级到规则 |
| 人工确认比例 | 哪些场景必须人工确认 |

原则：能由规则、约束和求解器解决的问题，不交给大模型；大模型只做异常理解、解释生成、规则候选和反馈结构化。可行性判断必须由求解器、质量门和人工确认兜底。

## 4. 数字孪生复刻案例

### 4.1 案例设定

案例编号：`reorch-poc-digital-twin-001`

场景：高混小批量离散制造单车间，CNC 设备发生故障后，需要判断哪些工单和工序受影响，并生成可执行的恢复方案。

数据结构：

| 项目 | 数字孪生设定 |
| --- | --- |
| 车间 | `WS-HMLV-01` |
| 工单 | 5 个 |
| 工序 | 16 个 |
| 资源 | 7 类设备/工位：CNC、车床、热处理、装配、质检、包装等 |
| 初始方案 | 生成 5 套，选择 `balanced` 作为基准 |
| 异常 | `CNC-02` 设备故障 |
| 故障等级 | `P2-High` |
| 预计维修 | 180 分钟 |
| 数据来源 | 内置数字孪生样本，不是客户生产数据 |

### 4.2 复刻流程

```text
1. 导入工单、工序、资源、日历、物料和换线规则
2. 生成初始排程方案，并选择 balanced 基准方案
3. 在异常发生时刻固化排程快照
4. 接入 CNC-02 设备故障事件
5. 计算受影响工单和工序
6. 选择恢复策略
7. 调用混合求解器生成候选方案
8. 经过质量门和数字孪生仿真评估
9. 生成回写预览，但不启用生产自动写回
10. 输出价值估算和审计包结构
```

### 4.3 系统输出

| 指标 | 数字孪生输出 |
| --- | --- |
| 受影响工单 | 2 个 |
| 受影响工序 | 5 个：`WO-9004-10`、`WO-9005-10`、`WO-9004-20`、`WO-9005-20`、`WO-9004-30` |
| 推荐策略 | `wait_and_repair` |
| 策略置信度 | 0.75 |
| 重排候选 | 1 个 |
| 质量门 | 通过 |
| 质量门置信度 | `medium` |
| 推荐策略 | `recommend_with_risk_warning` |
| 硬阻断 | 0 个 |
| 预警 | `Constraint coverage is limited; do not auto-preselect.` |
| 执行风险分 | 0.2462 |
| 风险标记 | `large_schedule_perturbation` |
| 冻结区违规 | 0 |
| 资源切换 | 0 |
| 回写预览 | 5 条指令 |
| 生产自动写回 | 关闭 |
| 计划员确认 | 必须 |

关键解释：

- 系统没有因为质量门通过就自动写回。
- 由于约束覆盖仍有限，系统明确给出风险提醒，不自动预选。
- 这个案例更适合说明 ReOrch 的工程边界：AI 和求解器给出候选，质量门和人工确认决定是否进入执行。

### 4.4 价值代理结果

| 指标 | 基准 | 数字孪生输出 | 变化 |
| --- | --- | --- | --- |
| 异常决策时间 | 90 分钟 | 8 分钟 | 节省 82 分钟 |
| 延期分钟 | 240 分钟 | 90 分钟 | 减少 150 分钟 |
| 换线次数 | 8 次 | 5 次 | 减少 3 次 |
| 加班时间 | 6 小时 | 2 小时 | 减少 4 小时 |
| 单次异常估算价值 | - | 7385 元 | 需客户财务口径复核 |

价值拆分：

| 项目 | 估算金额 |
| --- | --- |
| 计划员时间节省 | 205 元 |
| 延期减少 | 4500 元 |
| 换线减少 | 1800 元 |
| 加班减少 | 880 元 |
| 合计 | 7385 元 |

边界说明：上述价值是数字孪生代理测算，使用的是样本假设中的计划员小时成本、延期分钟成本、换线成本和加班成本。它证明系统已经具备“记录和计算价值”的结构，但不能直接写成客户现场 ROI。

### 4.5 这个案例应该如何放进路演

推荐放法：

> 在客户生产现场验证前，我们先用数字孪生复刻设备故障场景，完整跑通从排程快照、异常识别、影响分析、策略选择、候选方案、质量门、仿真、回写预览到价值估算的闭环。该样例中，系统识别 2 个受影响工单和 5 个受影响工序，生成 1 个通过质量门但带风险提醒的候选方案，估算节省 82 分钟决策时间、减少 150 分钟延期。我们不把它包装成客户 ROI，而是把它作为进入实验室 replay 和企业只读验证的证据模板。

不推荐放法：

> ReOrch 已经在真实工厂验证，每次异常可节省 7385 元。

## 5. 下一步如何把实验室采用升级为企业证据

| 阶段 | 目标 | 必交付物 |
| --- | --- | --- |
| 第 1 阶段：实验室受控采用 | 把数字孪生 case 跑成可重复 replay | case 表、截图、日志、source refs、反馈记录 |
| 第 2 阶段：实验室数据替换 | 用实验室真实或半真实数据替换内置样本 | 字段映射表、readiness report、约束缺口表 |
| 第 3 阶段：10-30 条 replay | 初步验证 Top-K 覆盖和失败归因 | replay casebook、采纳/微调/驳回统计 |
| 第 4 阶段：企业只读验证 | 用企业脱敏历史异常做对比 | 企业数据包、shadow report、验收指标 |
| 第 5 阶段：付费 PoC | 将价值代理替换为客户财务口径 | PoC 报告、ROI 区间、续费/扩展建议 |

最小尽调包：

```text
1. 实验室采用说明或合作邮件
2. 使用模块和日期记录
3. 10-30 条 replay case 表
4. 数据字段映射和脱敏说明
5. 每条 case 的输入、输出、质量门、人工反馈和失败归因
6. 数字孪生复刻报告
7. 不能外推为客户生产 ROI 的边界说明
```

## 6. 对投资人的最终口径

建议最终表达：

> ReOrch 当前已经完成 MVP 和数字孪生验证包，并进入合作实验室受控采用。我们已经能把一次设备故障复刻为可追溯的异常重决策链路：锁定排程快照，识别受影响工单和工序，生成候选恢复方案，通过质量门和仿真评估，再由计划员确认。实验室阶段的重点不是宣称生产 ROI，而是把每一次推荐、采纳、微调、驳回和失败归因记录下来，形成进入企业只读 replay 和 shadow mode 的证据资产。融资后，我们会把这套证据链迁移到 1-2 个设计合作企业的真实历史异常数据中，完成从实验室采用到付费 PoC 的转化。
