# ReOrch 从异常重决策到完整排产系统能力清单

版本：2026-07-04

## 1. 第一性原理

排产系统的本质不是画甘特图，而是在有限资源、复杂约束和动态扰动下持续回答：

1. 做什么：哪些订单、工单、工序应该进入计划。
2. 什么时候做：每道工序的开始、结束、等待、冻结和调整窗口。
3. 用什么做：设备、人员、工装、物料、外协和产线能力。
4. 为什么这样做：交期、成本、换线、瓶颈、库存、稳定性之间的取舍。
5. 计划变了怎么办：异常识别、影响分析、局部修复、全局重排、确认、回写和复盘。

因此，如果 ReOrch 要让企业合作后逐步不再依赖其他排产系统，必须从当前“异常重决策操作层”升级为“完整 AI APS / 排产操作系统”。

## 2. 当前已经具备的基础

- 异常接入、影响分析、策略选择。
- 候选方案生成和多目标评估。
- 质量门、人工确认、mock 回写。
- Data Readiness、Evidence Center、失败样本库。
- 受控 replay 采纳/微调/驳回记录。
- Incident Agent、Rule Candidate Agent、Feedback Agent 的低风险 AI 路由。
- P0 Reality Harness：canonical schema、样例客户数据包、字段 mapping 建议、readiness 权限闸门。
- Constraint Calibration：设备能力、资源日历、冻结窗口、换型规则编译，并阻断未发布或未回放通过的 AI 规则候选。
- Replay/Shadow Validation：Top-N 命中、质量门、资源匹配、时间偏差和 shadow readiness 评估。
- Shadow Mode Capture：advisory-only 记录计划员接受、微调、拒绝和 override，强制不生成回写命令。
- Agent Observability：统计 LLM steps、token、latency、fallback、guardrail 和成本建议。

当前可以支撑受控试用、历史 replay、shadow mode 和单场景 PoC，但不能直接替代完整 APS。

## 3. 必须补齐的完整能力

### 3.1 基础计划能力

- 需求导入：销售订单、预测需求、安全库存、补货需求。
- 主生产计划：日计划、周计划、月计划、滚动计划。
- 工单生成：订单拆分、合批、优先级、交期承诺。
- 计划版本：草稿、基准、审批中、已发布、已冻结、已回滚。
- 冻结窗口：冻结工序不可移动，或移动必须走审批。
- 计划发布：发布到 MES/APS/Excel/API，并支持撤回。

### 3.2 排程求解能力

- 初始排程：从零生成完整工序排程。
- 局部修复：只调整受影响区域。
- 全局重排：在较大扰动下重新优化。
- 滚动窗口排程：每天/每班次持续刷新。
- What-if 仿真：比较插单、缺料、设备故障、加班、外协等方案。
- 多目标优化：交期、makespan、换线、库存、设备利用率、加班、扰动最小化。
- 候选方案多样性：不只给一个最优解，而给保交付、保稳定、保成本等不同取舍。

### 3.3 约束库

- 工艺路线、前后依赖、替代工艺。
- 设备能力、并行设备、瓶颈资源。
- 人员技能、班次、休假、加班。
- 工装、夹具、模具、治具。
- 物料齐套、替代料、采购到货、库存占用。
- 质量 hold、返工、抽检、放行规则。
- 维护窗口、设备故障、产线停机。
- 外协产能、运输时间、供应商 SLA。
- 客户优先级、订单等级、违约成本。
- 换线、清线、批量、最小生产量。

### 3.4 数据模型和接口

- 标准对象：订单、工单、工序、资源、BOM、工艺路线、库存、日历、异常、反馈。
- ERP 接口：订单、物料、客户、交期、库存、采购。
- MES 接口：报工、设备状态、工序进度、生产反馈。
- WMS 接口：库存、出入库、齐套、库位。
- QMS 接口：质检状态、返工、放行、隔离。
- IoT 接口：设备状态、停机、稼动率、实时信号。
- API / 文件接口：CSV、Excel、JSON、REST、Webhook。
- 数据治理：字段映射、缺失检测、重复检测、血缘追踪、版本记录。

### 3.5 产品工作台

- 甘特图和资源负荷图。
- 订单视图、设备视图、物料视图、异常视图。
- 候选方案对比。
- 手动调整、拖拽、锁定、批量编辑。
- 多角色协同审批。
- 计划发布、回滚、差异对比。
- 执行反馈和复盘看板。
- 计划员偏好和案例库。

### 3.6 AI 使用边界

- AI 可参与：异常理解、规则候选、反馈归因、推荐解释、案例检索、自然语言问答。
- AI 不直接负责：硬约束求解、生产计划最终确认、自动回写、权限审批、质量门。
- 每类 Agent 必须有 schema、source refs、置信度、fallback、版本和审计。
- AI 成本必须记录模型、token、latency、调用原因和是否命中缓存。

### 3.7 质量门和安全

- 硬约束可行率：进入确认环节的方案必须 100% 通过硬约束。
- 数据 blocker：缺关键字段时不生成生产方案。
- 权限门：越权用户不能发布或回写。
- 回写门：必须支持预览、审批、幂等、防重复提交和回滚。
- 审计门：每次推荐和修改都能追溯输入、版本、约束、确认人和结果。
- 失败门：低置信、证据不足、冲突不可解时退回人工。

### 3.8 成本和性能

- 局部重排优先，避免每次全局求解。
- 缓存常见异常和模板解释。
- 小模型/规则优先，大模型只处理复杂语义。
- 求解超时返回最优已知可行解。
- 大规模压测：工单、工序、设备、异常并发、滚动窗口。
- 成本看板：每次求解、每次 Agent 调用、每次仿真的成本和耗时。

### 3.9 企业级部署

- 私有化部署和云部署。
- 多租户和权限隔离。
- 监控、告警、日志、备份、恢复。
- SLA 和应急预案。
- 安全测试、漏洞扫描、数据脱敏。
- 运维手册、接口文档、培训材料。
- 客户成功和持续优化机制。

### 3.10 商业验证

- 真实历史异常 replay：至少 10-30 条。
- Shadow mode：与计划员并行运行。
- Sandbox 回写：验证幂等、权限、回滚。
- 付费 PoC：明确验收指标和数据范围。
- 生产发布样板：至少 1 家客户真实使用 ReOrch 发布生产计划。
- 复制性验证：第二个客户定制成本下降。

## 4. 分阶段路线

### 阶段 1：异常重决策操作层

目标：接在 ERP/MES/APS 上方，解决设备故障、插单、缺料、返工后的快速重决策。

验收：历史 replay、shadow mode、人工确认、ROI 复盘。

### 阶段 2：AI APS 插件

目标：补齐初始排程、滚动排程、更多约束和系统适配器，成为现有 APS 的增强层。

验收：客户能用 ReOrch 生成可执行排程草案，并与原 APS 或人工方案对比。

### 阶段 3：单车间排产系统

目标：在一个车间内覆盖从订单导入、初始排程、异常重排、人工确认到发布回写的闭环。

验收：客户在真实业务中用 ReOrch 发布计划，原排产系统降级为备份或对照。

### 阶段 4：多车间 / 多工厂 AI 排产操作系统

目标：覆盖跨车间资源、供应链约束、外协、库存和集团级计划协同。

验收：形成行业模板、伙伴生态、企业级 SLA 和可复制收入。

## 5. 路演表达边界

可以说：

- ReOrch 当前从异常重决策切入。
- 长期可以向完整 AI APS 扩展。
- 已经具备部分初始排程、候选生成、质量门和 replay 证据。
- 替代传统排产系统需要分阶段验证。

不能说：

- 企业接入后马上不需要其他排产系统。
- 当前已经替代金蝶、用友或成熟 APS。
- AI 可以无人值守自动排产。
- 受控 replay 采纳率等同于客户生产 ROI。
