# 物料侧计划：从 BOM 到工序开工下限

排程回答“什么时候、在哪台设备上做”，物料侧回答“到那个时候料齐不齐”。这个模块把库存、在途和供应商的数据翻译成每道工序的齐套时间，交给求解器作为开工下限。

代码在 `app/services/supply/`，数据模型在 `app/models/supply.py`，接口在 `app/api/supply.py`。

## 输入

物料快照与排程快照配套导入（`POST /api/v1/supply/snapshots`）：

| 数据 | 说明 |
| --- | --- |
| BOM | 父件、子件、单位用量、损耗率 |
| 投料点 | 子件在工艺路线的哪道工序投入，按所需能力或工序位置指定；不指定则在首道工序 |
| 库存 | 现存、已分配、质量冻结、安全库存。可用量 = 现存 − 已分配 − 质量冻结 |
| 到货订单 | 承诺到货时间、状态（未发、在途、已到货、已放行）、缺项清单 |
| 计划参数 | 提前期、来料检验时长、批量倍数、最小订货量 |
| 工单需求 | 工单生产什么、多少 |
| 供应商交付记录 | 承诺时间、实际到货、数量、拒收数量、响应时长 |
| 替代料规则 | 主料、替代料、是否批准、批准人、依据 |

## 两个区分

**到货不等于可用。** 已到货的订单行可能还卡在来料检验、缺材质证明或缺附件上。每个卡点是一条缺项，有责任人和完成时间。只有“已放行”的行算库存；“已到货”的行要等所有未关闭缺项到期才可用；有一条缺项没写完成时间，这一行的可用时间就是未知，不会被当成可用。

**承诺不等于确定。** 已经过了承诺时间还没到的订单行，原来的日期已经不可信，可用时间记为未知，直到有新的承诺。供应商的历史交付决定一个新承诺可以信几分（见下文评分）。

## 齐套检查

`check_kits` 按需求时间把供给分配给需求：

1. 每种物料列出供给批次：现在可用的库存，加上每个到货订单行及其可用时间，按时间从早到晚。
2. 所有尚未开工的工序按计划开工时间排序，依次从最早的批次取料。已开工的工序视为已领料，不参与。
3. 一条需求的就绪时间是它用到的最后一个批次的可用时间；一道工序的齐套时间是它所有物料里最晚的那个。
4. 供给不够或者只剩可用时间未知的批次，这道工序记为“缺料，无时间”。

输出每道工序的状态（按时齐套、需等料多少分钟、缺料无时间）、齐套率和按时齐套率，并转成求解器的 `material_availability` 行。

两个可选开关：

- **按供应商风险调整**：把供应商历史延迟的第 80 百分位加到承诺时间上。
- **允许替代料**：主料不能按时齐套时，尝试用已批准的替代料整笔覆盖。未批准、缺批准人或缺依据的规则一律忽略。替代后原先分给这条需求的主料不会退回给后面的需求，结果偏保守。

## MRP 净需求

`run_mrp` 是标准的分时段记录逻辑。对每种物料、每个时间桶：

```text
预计结余[t] = 预计结余[t-1] + 在途到货[t] + 计划到货[t] − 毛需求[t]
```

结余低于安全库存时生成计划到货，按最小订货量和批量倍数取整，并按提前期前移成计划下达。物料按低层码从上到下处理，父件的计划下达在同一个桶里变成子件的毛需求。提前期不够、下达时间已经落在计划起点之前的数量单独列为“已错过下达”。

工单视为已确定，不在这里重新计划；它的子件需求按投料工序的开工时间进入毛需求。测试里有一个三层 BOM 的手算例，逐桶核对了结余、计划到货和计划下达。

## 到货与可用两层状态

`readiness_report` 对每个到货订单行给出：是否到货、是否可用、预计可用时间、未关闭缺项、已超期缺项。汇总里单列“已到货但不可用”的行数和“无责任人”的缺项数，这两个数是现场最容易被“货到了”掩盖的风险。

## 供应商评分

评分回答一个计划问题：这家供应商报的日期能信几分。四项指标各自折算到 0–1：

| 指标 | 权重 | 折算方式 |
| --- | --- | --- |
| 准时率 | 0.40 | 不晚于承诺时间加容差（默认 60 分钟）的交付占比 |
| 质量 | 0.30 | 1 − 拒收率 / 5%，下限 0 |
| 延迟幅度 | 0.20 | 1 − 平均延迟小时数 / 48，下限 0 |
| 响应 | 0.10 | 1 − 平均响应小时数 / 24，下限 0 |

加权后乘 100。85 分以上为 A，70 分以上为 B，其余为 C。没有响应数据时按其余三项重新归一。交付记录少于 3 次标为“未评级”，分数照常显示但不应作为决策依据。

权重和阈值是起步值，写在 `supplier_scorecard.py` 顶部，接入真实数据后应按企业自己的口径校准。

## 供应异常

物料短缺是主闭环里的一类异常（`incident_type = material_shortage`）。异常的 `resource_id` 是物料编号，细节在 `raw_payload` 里：

| 类型 | 含义 | 需要的字段 |
| --- | --- | --- |
| `eta_slip` | 到货推迟 | `new_promised_at`，可选 `order_id`、`line_id` |
| `quantity_short` | 到货数量不足，或库存盘亏 | `short_quantity` |
| `lot_rejected` | 来料检验不合格退回 | 可选 `new_promised_at`（补货时间） |

系统把事件应用到物料快照的副本上，前后各做一次齐套检查，得到新增等料的工序和新增缺料的工序（`GET /api/v1/incidents/{id}/material-impact`）。之后的影响分析、候选生成和确认见 [恢复上下文](recovery_context.md)。事件对不上快照（物料不存在、没有可推迟的订单行）时返回 422，不会被吞掉。

## 接口

| 接口 | 作用 |
| --- | --- |
| `POST /api/v1/supply/snapshots` | 导入物料快照；BOM 有环时拒绝 |
| `GET /api/v1/supply/kit-report` | 齐套检查，支持 `risk_adjusted`、`allow_substitutes` |
| `GET /api/v1/supply/mrp` | MRP 净需求，按自然日分桶 |
| `GET /api/v1/supply/readiness` | 到货与可用两层状态 |
| `GET /api/v1/supply/suppliers` | 供应商评分 |
| `GET /api/v1/incidents/{id}/material-impact` | 供应异常对齐套的影响 |

## 边界

- 物料快照目前只存在内存里，随排程快照重新导入，还没有进入持久化表结构。
- 分配规则是“按需求时间先到先得”，没有按工单优先级抢料，也没有跨工单的重新分配优化。
- MRP 是单工厂、无产能约束的净需求计算，不做批量合并优化，也不替代 ERP 的 MRP 运行；它的用途是让计划员在异常发生时看清缺口。
- 演示数据是合成的。评分权重、检验时长等参数没有经过任何真实企业数据校准。
