# 发运调度：恢复方案对到货的影响

生产恢复方案改的是完工时间，客户感受到的是到货时间。两个方案的工单延期数可能一样，但一个赶得上当班的车，另一个赶不上。发运模块把每个候选方案的完工时间接到车辆排线上，回答“选这个方案，今晚哪几票货会迟到，哪几票发不出”。

代码在 `app/services/dispatch/`，数据模型在 `app/models/dispatch.py`，接口在 `app/api/dispatch.py`。

## 问题

这是带时间窗的车辆路径问题，多了两条恢复场景需要的规则：

| 规则 | 说明 |
| --- | --- |
| 放行时间 | 一票货要等对应工单的最后一道工序完工才在月台上。车在它装的最后一票货放行后才能发车 |
| 软时间窗 | 异常之后有些时间窗注定赶不上。允许迟到并计入代价，结果给出“迟多少”，而不是一句“无可行解” |

车辆载重是硬约束。早到则等待。距离按平面直角坐标计算，单位公里。

## 代价

统一折算成公里：

```text
里程
+ 5    × 客户处迟到分钟数
+ 5    × 车辆超出班次的分钟数
+ 50   × 用车数
+ 5000 × 当班发不出的票数
```

权重在 `routing.Weights` 里，可按客户合同调整。当前取值的含义是：迟到一分钟相当于多跑五公里；一票货迟到超过约十六个小时，就不如留到下一班。这些数字是演示默认值，没有用真实运费和违约条款校准。

## 求解

自适应大邻域搜索：

1. 按时间窗截止顺序做一次最便宜插入，得到初始解。
2. 每一步拆掉几票货（随机、位置最差、时空相近三选一），再装回去（最便宜插入或 regret-2）。
3. 用模拟退火决定是否接受变差的解；每 50 步按各算子的表现调整选用概率。

同一个随机种子的结果完全一致。十来票货的规模一秒内完成。

## 怎么知道它算得对

| 检查 | 做法 | 位置 |
| --- | --- | --- |
| 小规模最优性 | 6 票货、2 辆车时枚举全部分配和顺序，搜索结果的代价必须与枚举相同 | `test_search_matches_enumeration_on_small_problems` |
| 与独立求解器对照 | 25 票货、硬时间窗、无放行时间的算例上，OR-Tools 路径求解器跑两秒，搜索结果不得比它差 3% 以上 | `test_search_is_competitive_with_ortools_routing` |
| 代价自洽 | 返回的代价等于按返回路线重新算一遍的代价 | `test_reported_cost_is_the_cost_of_the_returned_routes` |
| 放行规则 | 放行晚的那票单独走一车时更便宜，就不会拖住整车 | `test_late_release_is_carried_separately_when_that_is_cheaper` |

没有用 Solomon 标准算例做对照。那组算例是硬时间窗、不带放行时间，目标是先最少车辆再最短里程，与这里的代价定义不同，分数不能直接比较。

## 与闭环的衔接

`GET /api/v1/incidents/{id}/dispatch-impact` 对原计划和每个可行的候选方案各排一次线，并排返回。工作台在方案比较下方显示同一张表。

演示数据（`demo/data/dispatch/`）是 8 票当晚发运的货和 3 辆车：

| 场景 | 方案 | 迟到 | 当班发不出 |
| --- | --- | --- | --- |
| 设备故障 | 重排 | 0 票 | 0 票 |
| 设备故障 | 只顺延不调整 | 2 票，共 99 分钟 | 0 票 |
| 供应延期 | 重排，等待到货 | 0 票 | 1 票 |
| 供应延期 | 重排，使用已批准替代料 | 0 票 | 0 票 |
| 供应延期 | 只顺延不调整 | 0 票 | 2 票 |

## 边界

- 一辆车一班只跑一趟，不回场二次装车。
- 距离是直线距离乘以固定车速，没有接地图和路况。
- 发运数据只存在内存里。
- 发运结果目前只用于展示和比较，不参与候选方案的评分。
