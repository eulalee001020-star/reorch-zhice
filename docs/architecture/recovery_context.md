# 恢复上下文：把异常的物理事实变成约束

一次异常改变了三件排程快照里没有的事：从什么时候开始重排、什么资源不可用、物料什么时候能用。恢复上下文把这三件事写成求解器和校验器本来就认识的约束行，所以求解器不需要知道自己在处理哪一类异常。

代码在 `app/services/intake/`：`recovery_context.py`、`right_shift.py`、`recovery_planning.py`、`recovery_flow.py`。

## 三类事实

| 事实 | 来源 | 写入快照的位置 |
| --- | --- | --- |
| 决策时点 | 异常的 `occurred_at` | `operation_release_constraints`：未开工工序不得早于决策时点 |
| 资源不可用 | 设备故障的预计修复时长 | `resource_calendar`：故障设备在 `[发生, 发生 + 时长)` 不可用 |
| 物料可用时间 | 齐套检查（见 [物料侧计划](supply_planning.md)） | `material_availability`：工序不得早于齐套时间开工 |

预计修复时长先取异常载荷里的 `estimated_duration_minutes`，没有就从描述文字里解析（“预计维修 4 小时”）。两处都没有时不生成不可用窗口，并在上下文里记一条 `repair_time_unknown`，不会假设一个数。

## 已发生的不能改

决策时点之前已经开工的工序是历史，全部冻结。唯一的例外是故障发生时正在故障设备上加工的那道工序：它被打断，需要重新安排，按保守口径整道重做。

如果排程里所有工序都早于决策时点，说明没有可重排的内容，不生成上下文，流程退回原有的估算逻辑。

## 只顺延基准

`right_shift` 回答“什么都不调整会怎样”：每道工序留在原设备、保持原顺序，只在不得不推的时候往后推。推它的原因只会是下面之一，取最晚的那个：

1. 被打断，从决策时点重新开始；
2. 前序工序结束；
3. 同一设备上排在它前面的工序结束；
4. 物料齐套；
5. 所在设备的不可用窗口结束。

这个基准有三个用途。

**影响分析以它为准。** 工序延误是开工推迟了多久，工单延误是完工推迟了多久，合计按工单加总，同一原因推迟的一串工序只算一次。工单完工晚于交期记为违约；没违约但延误吃掉了事发前一半以上的余量，记为预警。

**它是候选方案之一。** 基准通过与其他候选相同的独立约束校验后，作为“只顺延不调整”方案返回，排在最后。重排方案值不值得采纳，看它比基准好多少。

**“等待修复”策略直接返回它。** 等待就是顺延，不需要搜索。

## 候选方案怎么生成

1. 用上下文生成带约束的快照副本，原快照不改。
2. 清空影响报告里的逐工序延误估计再交给求解器。那些数字描述的是“等待”，如果保留，改到别的设备上的工序也会被迫等同样长的时间。
3. 候选之间按目标区分（均衡、扰动最小、交付优先），完全相同的排程只保留一个。
4. 物料异常且存在已批准的替代料时求解两次：等待到货、使用替代料。两种方案都返回，方案上标明用的是哪一种。
5. 确认时按所选方案当时使用的约束重新校验。

REST 接口和 Agent 工作流都走 `recovery_flow` 里的同一套实现。

## 边界

- 被打断的工序按整道重做处理，没有建模“已完成 60%，剩余 40%”。
- 修复时长是单点估计，没有区间。修复提前或延后需要重新触发。
- 没有可用时间的缺料（没有在途、没有替代料）无法给出可行方案，系统会如实返回“无可采纳候选”，不会排一个没有料的计划。
- 策略选择仍是规则：等待会导致违约时不选等待；受影响工单超过两成或存在违约时选全局重排。
